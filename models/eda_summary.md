# Exploratory Data Analysis — Feature Dataset

Generated by [`eda.py`](eda.py) against the actual committed
[`data/features.xlsx`](../data/features.xlsx) joined with `is_fraud` from
[`data/transactions_raw.xlsx`](../data/transactions_raw.xlsx). Every number
below is a real computed statistic — nothing here is fabricated.

## Sample size caveat (read this first)

**N = 8.** `data/features.xlsx` currently holds only the 8 sample rows
committed during initial scaffolding, not real pipeline output. Every
statistic below is technically correct for those 8 rows, but **none of the
conclusions are statistically robust** — correlations computed on 8 points
are extremely sensitive to individual outliers, and the class-balance ratio
is not representative of a real transaction stream. Treat this document as
a demonstration of the EDA methodology and re-run `eda.py` once the
producer/pipeline have generated a meaningful volume of records (tracked
under SCRUM-20 and SCRUM-23), not as a final basis for model design
decisions.

## Class balance

| is_fraud | count |
|---|---|
| False | 5 |
| True | 3 |

3/8 (37.5%) of the sample rows are fraud. This is wildly higher than any
real-world fraud rate (the producer's own `FRAUD_RATE` default is 2%) —
purely an artifact of the small hand-picked sample, not a real signal.

## Missing values

Zero missing values across all four feature columns and `is_fraud`. All
Excel writers append complete rows, so this is expected and should stay
true at any scale — worth re-checking once real volume exists, since a
`None`/blank cell from a partial write would show up here.

## Correlation matrix

See [`eda_output/correlation_heatmap.png`](eda_output/correlation_heatmap.png).

`velocity_1h` (r=0.92), `bin_spend_rate` (r=0.88), and
`terminal_reversal_count` (r=0.86) all show strong positive correlation
with `is_fraud` in this sample; `geo_jump_km` is weaker (r=0.47). Given the
N=8 caveat above, don't read these as confirmed feature importances — they
happen to line up with how the synthetic fraud scenarios were designed
(`cloned_card` inflates amount, `agent_collusion` clusters velocity,
`fake_reversal` swaps BIN), which is circular by construction, not an
independent signal.

## Class imbalance strategy

Real-world POS fraud is rare (this project's own producer defaults to a factor of 2% `FRAUD_RATE`), so class imbalance will be severe once real volume
exists. Recommendation for [`train_xgboost.py`](train_xgboost.py):

- Use **`scale_pos_weight`** (ratio of negative to positive class count) in
  `XGBClassifier` rather than oversampling/SMOTE. XGBoost's built-in
  weighting is simpler to reason about and avoids synthesizing fake
  minority-class feature vectors for a fraud-detection use case where the
  minority class's exact feature values matter.
- Revisit this recommendation once real data volume exists — if the
  positive class turns out to be extremely sparse (<0.5%), SMOTE or a
  combination of `scale_pos_weight` + threshold tuning may be worth
  comparing empirically instead of taking this recommendation on faith.
