# DAT608 — POS Agent Fraud Detection

[![CI](https://github.com/aganrandave/DAT608-POS-Fraud-Detection/actions/workflows/ci.yml/badge.svg)](https://github.com/aganrandave/DAT608-POS-Fraud-Detection/actions/workflows/ci.yml)

A real-time fraud detection system for Nigerian point-of-sale (POS) agent
transactions. Synthetic transactions are streamed through Kafka, enriched
with rolling features in Spark Structured Streaming, scored by an ensemble
of XGBoost and Isolation Forest models tracked in MLflow, and surfaced as
tiered alerts through ksqlDB and a Streamlit dashboard. The project is a
DAT608 Big Data capstone at Pan-Atlantic University.

## Scope, data, and limitations

**This is a university capstone prototype, not a production fraud system.**
It demonstrates an end-to-end real-time ML pipeline architecture, and the
engineering practices (MLflow model governance, CI verification, honest
reporting of what's measured versus assumed) are built to a real standard -
but the system has not been validated against real transactions, and
several production-grade controls are intentionally out of scope. Read this
section before citing any number elsewhere in this repository.

- **All data is simulated.** Every transaction is generated by
  [`producer/`](producer/), with Nigerian-shaped distributions (states,
  LGAs, card BINs, NIBSS/EFInA-informed amount bands) but no real customer,
  card, or merchant data anywhere in this repository. There is no PII.
- **Fraud labels are injected, not observed.** `is_fraud` and `fraud_type`
  (`cloned_card`, `agent_collusion`, `fake_reversal`) come from the
  generator's own fraud-scenario logic (see
  [`producer/fraud_scenarios.py`](producer/fraud_scenarios.py)), not from a
  real investigation or chargeback outcome. Reported model performance
  measures how well the models recover patterns this project's own
  generator deliberately created - it is **not** evidence of performance on
  real Moniepoint, NIBSS, or industry transaction data, and must not be
  cited as such.
- **The Excel/Git persistence layer is a demonstration choice.** Storing
  state in `.xlsx` workbooks under [`data/`](data/) (see
  [Data store](#data-store) below) makes every data change reviewable in a
  pull request, which suited this project's grading and collaboration
  needs. It is explicitly not a feature store or transactional database:
  no concurrent-write guarantees beyond file locking, no row-level access
  control, no query layer, and no retention policy.
- **A production implementation would additionally need:** controlled
  access to real transaction data under a proper data-sharing agreement; a
  durable database or feature store in place of Excel; schema and lineage
  controls; encryption at rest and in transit; secrets management (this
  project's `.env` pattern is dev-only); model calibration against real,
  investigator-confirmed fraud labels rather than synthetic ones; drift
  monitoring on both data and model performance; a fairness and privacy
  review before scoring real customers; a feedback loop from fraud
  investigators back into labeling and retraining; and governed model
  promotion (approvals, rollback, canarying) in place of this project's
  single-environment auto-promote-to-Production pattern (see
  [models/README.md](models/README.md)).

None of this diminishes what the prototype actually demonstrates: a real,
working, measured streaming ML pipeline, built and verified with the same
rigor a production system would demand at this stage - it just hasn't
cleared the additional bar real deployment requires, and this README says
so plainly rather than leaving that gap implicit.

## Architecture overview

```
 +-------------+     +-------+     +------------------+     +---------------------+
 | Transaction | --> | Kafka | --> | Spark Structured | --> | Feature Store       |
 | Generator   |     | Topic |     | Streaming        |     | (data/features.xlsx)|
 +-------------+     +-------+     +------------------+     +----------+----------+
                                                                       |
                                                                       v
                                                          +------------------------+
                                                          | XGBoost + Isolation    |
                                                          | Forest (MLflow logged) |
                                                          +------------+-----------+
                                                                       |
                                                                       v
+--------------+     +------------+     +----------+     +-------------------------+
| Streamlit    | <-- |  Alerts    | <-- | ksqlDB   | <-- | FastAPI Scoring Service |
| Dashboard    |     | (alerts.   |     | Alert    |     | (data/fraud_scores.xlsx)|
|              |     |  xlsx)     |     | Logic    |     |                         |
+--------------+     +------------+     +----------+     +-------------------------+
```

All services are orchestrated with Docker Compose — see [infra/README.md](infra/README.md).

## Quickstart

```bash
git clone https://github.com/aganrandave/DAT608-POS-Fraud-Detection.git
cd DAT608-POS-Fraud-Detection
cp .env.example .env
docker compose up --build
```

The Streamlit dashboard will be available at `http://localhost:8501` and the
FastAPI scoring service at `http://localhost:8000/docs`.

## Data store

This project uses **Excel files instead of a live database**. Every
persistent record — raw transactions, engineered features, model scores,
and alerts — lives under [`data/`](data/) as a tracked `.xlsx` file
(`data/transactions_raw.xlsx`, `data/features.xlsx`, `data/fraud_scores.xlsx`,
`data/alerts.xlsx`, `data/reference/terminals.xlsx`,
`data/reference/merchants.xlsx`). Because these files are committed to Git,
every pull request carries its data alongside the code that produced it,
and reviewers can diff data changes the same way they diff code. Each layer
reads and writes these files through a shared `openpyxl` + `filelock`
pattern implemented in that layer's `excel_reader.py` / `excel_writer.py`.
